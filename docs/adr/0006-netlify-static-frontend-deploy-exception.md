# Netlify static-frontend deploy: a narrow exception to the local-only decision

#3's tech stack call settled on fully local deploy (`docs/spec.md`: "no hosting — financial data never leaves the machine"), because there was no reason yet to expose anything and every reason not to expose real financial data. #64 asks for shareable PR previews and a persistent look at `master` without reopening that decision wholesale, so this ADR carves out one narrow exception instead of amending the local-only rule itself.

**What's exempted:** `apps/web`'s static build only. Netlify's native git integration (repo connected via its dashboard — a human-only OAuth/build-settings step, not something this ADR or its config can do) builds and serves that static output for both PR deploy previews and a persistent `master` production deploy. `apps/server` and the database are never built, deployed, or reachable from either environment — nothing this exception touches can read or write real financial data, because nothing it touches has a backend to ask. The build config (`netlify.toml` at repo root) scopes the build command and publish directory to `apps/web` specifically so a future edit can't accidentally widen this to include the server.

**Why not amend the local-only line instead:** the local-only decision is still correct for anything that touches real data or a backend; this is a frontend-shell exception, not a reversal. A separate ADR keeps the original decision's reasoning intact and gives this exception, and its tripwire, a durable home of its own rather than a caveat buried in spec prose.

**Staying unindexed:** both preview and production deploys ship `robots.txt` (`Disallow: /`) and a `noindex, nofollow` meta tag in `apps/web/index.html`, applied uniformly since both environments share the same build. There's no auth in front of either (per #4 — settled by the local-only decision this exception carves into), so staying out of search indexes and unlisted is the only gate the deployed shell has; belt-and-suspenders since either mechanism failing shouldn't be the sole safeguard.

**No live API calls today:** as of this exception, `apps/web` has no `fetch`/`/api` calls at all — only route stubs. Nothing needs redirecting to a static JSON fixture yet, so none was added. If a future screen adds a live call before a backend is worth hosting publicly, it must be backed by a static fixture, not point at `apps/server`.

**Tripwire:** revisit this exception — and the noindex/no-backend constraints it depends on — before any screen reads or writes real financial data. At that point the local-only decision's original reasoning applies again in full, and either the Netlify deploy needs to go away or a real hosting/auth decision (superseding #4) needs to be made first.
